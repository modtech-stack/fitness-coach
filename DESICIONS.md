# Decision 001
## GitHub является источником истины проекта

Дата:
2026-07-26

Статус:
Принято

Решение:

GitHub используется как основное хранилище:

- документации;
- архитектуры;
- кода;
- истории изменений.

Причина:

Проект создаётся с использованием AI-инструментов.
Необходимо иметь единую структуру знаний и историю изменений.

Альтернативы:

Google Docs.

Почему не выбрано:

Удобен для текста, но хуже подходит для совместной разработки с Codex.

# Decision 002
## Разделение Product / Knowledge / Profile

Дата:
2026-07-26

Статус:
Принято

Решение:

Проект разделяется на три слоя:

## docs

Описание продукта и архитектуры.

## knowledge

База знаний предметной области.

## profiles

Данные конкретных пользователей.

Причина:

Универсальные правила тренировок не должны смешиваться с персональными настройками.

Пример:

Правило:

"Недосып снижает способность выполнять интенсивную нагрузку"

находится в knowledge.

Правило:

"Борис после перелётов снижает интенсивность"

находится в profiles.

# Decision 004
## Training Engine строится на правилах, а не на одном readiness score

Дата:
2026-07-26

Статус:
Принято

Решение:

Не использовать единую оценку:

"готовность сегодня = 85%"

Вместо этого использовать набор факторов:

- сон;
- самочувствие;
- симптомы;
- нагрузка;
- боль;
- тренды показателей.

Причина:

Один показатель не отражает сложность восстановления человека.

# Decision 011
## Создание тренировочной программы требует этапа проектирования и проверки

Дата:
2026-07-26

Статус:
Принято

## Решение

В MVP тренировочная программа создаётся не автоматически в один шаг.

Процесс:

1. Пользователь задаёт:
- цель;
- ограничения;
- доступное время;
- оборудование;
- опыт;
- предпочтения;
- состояние здоровья.

2. GPT создаёт предложение программы:

- макроцикл;
- мезоциклы;
- микроциклы;
- упражнения;
- объём;
- интенсивность;
- периодизацию;
- прогрессию нагрузки.

3. Программа проходит экспертный аудит.

В MVP:
- Борис выполняет роль эксперта для себя и жены.

В будущем:
- сертифицированный тренер может проводить аудит программ клиентов.

4. После подтверждения программа становится активной.

5. В процессе выполнения программа может корректироваться на основании обратной связи.

---

## Причина

Создание долгосрочной тренировочной программы требует контекстного понимания:

- цели;
- ограничений;
- тренировочного опыта;
- восстановления;
- доступных ресурсов.

LLM может быстро создавать варианты программ, но требует проверки логики и соответствия целям.

---

## Будущее развитие

Вместо генерации программы "с нуля":

GPT использует библиотеку проверенных тренировочных блоков:

- силовые блоки;
- гипертрофия;
- развитие силы;
- аэробная база;
- интервальные блоки;
- восстановительные блоки.

GPT выступает как архитектор программы, собирающий блоки под пользователя.
