# 1. Назначение

Этот документ описывает основные сущности данных MVP.

Цель:

создать структуру хранения данных для:

- пользователей;
- тренировочных программ;
- выполнения тренировок;
- восстановления;
- адаптации нагрузки.

# 2. Основной принцип

Все пользовательские данные связаны через user_id.

Каждый пользователь имеет:

- собственный профиль;
- собственные цели;
- собственные программы;
- собственную историю тренировок.

# 4. Профиль пользователя


Profile


Хранит:


- возраст;
- пол;
- рост;
- вес;
- тренировочный опыт;
- уровень активности;
- оборудование;
- предпочтения.


Связь:

User → Profile

В Этапе 1 один пользователь имеет не более одного профиля.
`profiles.user_id` уникален и ссылается на `auth.users.id`.

В Stage 1.5:

- `training_experience` хранит конкретную длительность регулярного
  опыта: `none`, `under_6_months`, `six_months_to_two_years`,
  `over_two_years`;
- `activity_level` описывает повседневную активность вне тренировок:
  `low`, `moderate`, `high`;
- старые значения мигрируются без удаления профилей:
  `beginner → under_6_months`, `intermediate →
  six_months_to_two_years`, `advanced → over_two_years`;
- активность мигрируется так:
  `sedentary → low`, `light/moderate → moderate`,
  `very_active → high`.

# 5. Цели


Goal


Примеры:

- рекомпозиция;
- снижение веса;
- набор массы;
- выносливость;
- здоровье.


Поля:

- type
- target_value
- start_date
- end_date
- status

В реализованном минимальном домене приоритет хранится как:

- `1` — основная цель;
- `2` — второстепенная цель.

Частичный уникальный индекс гарантирует не более одной активной
основной цели на пользователя. При назначении новой активной основной
цели триггер автоматически переводит прежнюю в разряд второстепенных.
Старые приоритеты `2–5` безопасно приводятся к `2`.

# 6. Ограничения


Constraints


Хранят:

- травмы;
- ограничения здоровья;
- доступное время;
- оборудование;
- предпочтения.

В Stage 1.5 пользователь выбирает один из типов:

- `pain`;
- `injury`;
- `health`;
- `schedule`;
- `equipment`;
- `other`.

Старое значение `preference` сохраняется как `other`. Поле `severity`
остаётся в базе, но допускает `NULL`, не запрашивается у пользователя и
зарезервировано для будущей оценки риска Training Engine.

## Безопасность минимального домена

Для `profiles`, `goals` и `constraints` включён Row Level Security.

Пользователь с ролью `authenticated` может читать, создавать, изменять
и удалять только строки, где `user_id = auth.uid()`. Роль `anon` не
получает доступ к этим таблицам. Server Actions всегда получают
`user_id` из проверенной Auth-сессии, а не из формы пользователя.

Все три внешних ключа на `auth.users.id` имеют `ON DELETE CASCADE`.
Полное удаление аккаунта выполняется server-only вызовом Supabase Admin
API для идентификатора текущего проверенного пользователя. Удаление
строки Auth и каскад связанных данных происходят целостно на стороне
PostgreSQL; `service_role` key не передаётся в браузер.
