# 1. Назначение

Этот документ описывает основные сущности данных MVP.

Цель:

создать структуру хранения данных для:

- пользователей;
- тренировочных программ;
- выполнения тренировок;
- восстановления;
- адаптации нагрузки.


---

# 2. Основной принцип

Все пользовательские данные связаны через user_id.

Каждый пользователь имеет:

- собственный профиль;
- собственные цели;
- собственные программы;
- собственную историю тренировок.


---

# 3. Пользователь


User

Основная сущность.


Поля:

- id
- email
- created_at
- role


Роли:

- user
- reviewer
- trainer
- admin


---

# 4. Профиль пользователя


Profile


Хранит:


- возраст;
- пол;
- рост;
- вес;
- тренировочный опыт;
- уровень активности;
- оборудование;
- предпочтения.


Связь:

User → Profile

В Этапе 1 один пользователь имеет не более одного профиля.
`profiles.user_id` уникален и ссылается на `auth.users.id`.

В Stage 1.5:

- `training_experience` хранит конкретную длительность регулярного
  опыта: `none`, `under_6_months`, `six_months_to_two_years`,
  `over_two_years`;
- `activity_level` описывает повседневную активность вне тренировок:
  `low`, `moderate`, `high`;
- старые значения мигрируются без удаления профилей:
  `beginner → under_6_months`, `intermediate →
  six_months_to_two_years`, `advanced → over_two_years`;
- активность мигрируется так:
  `sedentary → low`, `light/moderate → moderate`,
  `very_active → high`.


---

# 5. Цели


Goal


Примеры:

- рекомпозиция;
- снижение веса;
- набор массы;
- выносливость;
- здоровье.


Поля:

- type
- target_value
- start_date
- end_date
- status

В реализованном минимальном домене приоритет хранится как:

- `1` — основная цель;
- `2` — второстепенная цель.

Частичный уникальный индекс гарантирует не более одной активной
основной цели на пользователя. При назначении новой активной основной
цели триггер автоматически переводит прежнюю в разряд второстепенных.
Старые приоритеты `2–5` безопасно приводятся к `2`.


---

# 6. Ограничения


Constraints


Хранят:

- травмы;
- ограничения здоровья;
- доступное время;
- оборудование;
- предпочтения.

В Stage 1.5 пользователь выбирает один из типов:

- `pain`;
- `injury`;
- `health`;
- `schedule`;
- `equipment`;
- `other`.

Старое значение `preference` сохраняется как `other`. Поле `severity`
остаётся в базе, но допускает `NULL`, не запрашивается у пользователя и
зарезервировано для будущей оценки риска Training Engine.

## Безопасность минимального домена

Для `profiles`, `goals` и `constraints` включён Row Level Security.

Пользователь с ролью `authenticated` может читать, создавать, изменять
и удалять только строки, где `user_id = auth.uid()`. Роль `anon` не
получает доступ к этим таблицам. Server Actions всегда получают
`user_id` из проверенной Auth-сессии, а не из формы пользователя.

Все три внешних ключа на `auth.users.id` имеют `ON DELETE CASCADE`.
Полное удаление аккаунта выполняется server-only вызовом Supabase Admin
API для идентификатора текущего проверенного пользователя. Удаление
строки Auth и каскад связанных данных происходят целостно на стороне
PostgreSQL; `service_role` key не передаётся в браузер.

# 7. Тренировочная программа

`training_programs` — корень пользовательского плана.

Реализованные статусы:

- `draft`;
- `under_review`;
- `approved`;
- `active`;
- `needs_adjustment`;
- `completed`;
- `archived`.

Частичный уникальный индекс допускает не более одной активной программы
на пользователя. В Stage 2 пользователь явно создаёт одну синтетическую
подготовленную программу через `create_starter_program()`. Функция
идемпотентна и не использует GPT.


---

# 8. Фазы программы

`program_phases` хранит упорядоченные фазы активной программы:

- название и описание;
- номер фазы;
- даты начала и окончания.

Связь: `training_programs → program_phases`.


---

# 9. Недели программы

`program_weeks` хранит номер и календарные границы недели.

Связь: `program_phases → program_weeks`.


---

# 10. Запланированная тренировка

`planned_workouts` хранит неизменяемую в рамках выполнения часть плана:

- название и фокус;
- инструкции;
- календарную дату;
- ожидаемую длительность;
- порядок внутри недели.

Связь: `program_weeks → planned_workouts`.


---

# 11. Запланированное упражнение

`planned_exercises` хранит:

- название;
- плановое количество подходов и повторений;
- целевой вес и RPE, если они заданы;
- подсказку и порядок в тренировке.

Связь: `planned_workouts → planned_exercises`.


---

# 12. Выполненная тренировка

`workout_sessions` хранит факт выполнения отдельно от плана:

- связь с запланированной тренировкой;
- статус;
- время начала и завершения;
- комментарий пользователя.

Ограничение допускает не более одного результата для одной плановой
тренировки пользователя.

# 13. Фактические подходы

`actual_sets` хранит для каждого выполненного подхода:

- упражнение и номер подхода;
- фактические повторения;
- фактический вес, если применимо;
- RPE по шкале 1–10.

Функция `complete_workout()` проверяет владельца, принадлежность
упражнений тренировке, диапазоны значений и дубликаты, затем атомарно
создаёт `workout_sessions` и все `actual_sets`.

# 14. Безопасность тренировочного домена

Все семь таблиц Stage 2 содержат `user_id`. Составные внешние ключи
не позволяют связать строки разных пользователей. RLS разрешает роли
`authenticated` читать только свои строки, а `anon` не получает доступа.
Прямое изменение тренировочных таблиц клиентом запрещено: разрешённые
записи выполняют только проверяющие функции `create_starter_program()` и
`complete_workout()`. Удаление пользователя каскадно удаляет программу и
историю.
