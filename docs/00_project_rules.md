# AI Fitness Trainer
# Project Rules v1.0

Дата создания: 2026-07-25

---

# 1. Назначение документа

Этот документ определяет правила разработки проекта AI Fitness Trainer.

Он нужен для того, чтобы при работе человека и AI-разработчиков сохранялись:

- единое понимание продукта;
- последовательность решений;
- минимальная сложность;
- фокус на ценности для пользователя.

---

# 2. Главный принцип проекта

Мы создаём не просто приложение.

Мы создаём систему принятия решений для персонального тренировочного процесса. 

Сначала безопасность, затем устойчивость плана, затем прогресс, и только потом оптимизация.

Главный вопрос продукта:

> "Что конкретному человеку нужно делать сегодня, чтобы двигаться к своей цели?"

---

# 3. Принцип MVP

Первое правило:

> Сначала рабочая ценность, потом масштабирование.

Не создаём заранее:

- сложный дизайн;
- множество интеграций;
- социальные функции;
- коммерческую инфраструктуру;
- сложные алгоритмы без необходимости.

Каждая новая функция должна отвечать на вопрос:

"Помогает ли это пользователю принимать лучшее решение по тренировочному процессу?"

---

# 4. Роль AI в проекте

AI используется как:

- разработчик;
- технический консультант;
- аналитик;
- помощник пользователя.

Но AI не является владельцем бизнес-решений.

AI не должен самостоятельно:

- менять ключевую концепцию продукта;
- усложнять архитектуру без необходимости;
- добавлять функции вне MVP;
- менять тренировочную философию без согласования.

---

# 5. Принцип разработки

Работаем маленькими итерациями.

Цикл:

1. Сформулировать проблему.
2. Предложить решение.
3. Объяснить архитектуру.
4. Реализовать минимальную версию.
5. Проверить работу.
6. Зафиксировать результат.

---

# 6. Правила для Codex / AI-разработчиков

Перед написанием кода:

AI должен:

1. Объяснить, что будет сделано.
2. Объяснить зачем это нужно.
3. Предложить минимальный вариант реализации.
4. Указать возможные ограничения.

После написания кода:

AI должен:

1. Проверить результат.
2. Объяснить изменения.
3. Объяснить, что изучил пользователь.
4. Предложить следующий маленький шаг.

---

# 7. Принцип простоты архитектуры

Предпочтение отдаётся:

простое решение,
которое работает,

вместо:

идеального решения,
которое сложно поддерживать.

---

# 8. Документирование решений

Важные решения фиксируются в документации.

Если принято решение:

- изменить архитектуру;
- добавить новую функцию;
- отказаться от подхода;

это должно быть отражено в документах проекта.

---

# 9. Разделение ответственности

## Product Owner

Борис:

- определяет ценность продукта;
- принимает продуктовые решения;
- определяет приоритеты.

## AI Developer

Codex:

- реализует технические решения;
- предлагает варианты;
- пишет код.

## AI Architect

ChatGPT:

- помогает проектировать систему;
- проверяет решения;
- помогает сохранять целостность продукта.

---

# 10. Критерий успеха

Проект успешен, если:

пользователь получает понятное решение,

а не просто красивый интерфейс и большое количество данных.
