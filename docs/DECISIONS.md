# Decision 001
## GitHub является источником истины проекта

Дата:
2026-07-26

Статус:
Принято

Решение:

GitHub используется как основное хранилище:

# Decision 002
## Разделение Product / Knowledge / Profile

Дата:
2026-07-26

Статус:
Принято

Решение:

Проект разделяется на три слоя:

## docs

Описание продукта и архитектуры.

## knowledge

База знаний предметной области.

## profiles

Данные конкретных пользователей.

Причина:

Универсальные правила тренировок не должны смешиваться с персональными настройками.

Пример:

Правило:

"Недосып снижает способность выполнять интенсивную нагрузку"

находится в knowledge.

Правило:

"Для тестового пользователя после перелёта снижается интенсивность"

находится в profiles.

# Decision 011
## Создание тренировочной программы требует этапа проектирования и проверки

Дата:
2026-07-26

Статус:
Принято

## Решение

В MVP тренировочная программа создаётся не автоматически в один шаг.

Процесс:

1. Пользователь задаёт:
- цель;
- ограничения;
- доступное время;
- оборудование;
- опыт;
- предпочтения;
- состояние здоровья.

2. GPT создаёт предложение программы:

- макроцикл;
- мезоциклы;
- микроциклы;
- упражнения;
- объём;
- интенсивность;
- периодизацию;
- прогрессию нагрузки.

3. Программа проходит экспертный аудит.

В MVP:
- назначенный Program Reviewer проверяет программы пилотных пользователей.

В будущем:
- сертифицированный тренер может проводить аудит программ клиентов.

4. После подтверждения программа становится активной.

5. В процессе выполнения программа может корректироваться на основании обратной связи.

---

## Причина

Создание долгосрочной тренировочной программы требует контекстного понимания:

- цели;
- ограничений;
- тренировочного опыта;
- восстановления;
- доступных ресурсов.

LLM может быстро создавать варианты программ, но требует проверки логики и соответствия целям.

---

## Будущее развитие

Вместо генерации программы "с нуля":

GPT использует библиотеку проверенных тренировочных блоков:

- силовые блоки;
- гипертрофия;
- развитие силы;
- аэробная база;
- интервальные блоки;
- восстановительные блоки.

GPT выступает как архитектор программы, собирающий блоки под пользователя.

# Decision 013
## Main является единственным источником истины

Дата:
2026-07-27

Статус:
Принято

Решение:

Весь актуальный продуктовый, архитектурный и предметный контекст хранится в каталогах ветки `main`.

Новый разработчик должен получить полную актуальную картину проекта после клонирования только `main`.

Причина:

Разделение документов между независимыми ветками скрывает часть контекста, создаёт расхождения и делает внутренние ссылки ненадёжными.

---

# Decision 014
## Тематические ветки не используются как постоянное хранилище документации

Дата:
2026-07-27

Статус:
Принято

Решение:

Рабочие ветки могут временно использоваться для подготовки изменений, но после review актуальная документация должна попадать в `main` через Pull Request.

Ветки `docs`, `knowledge`, `profile`, `training` и аналогичные им не являются отдельными источниками истины.

Причина:

Документы разных типов должны различаться каталогами, а не постоянными ветками.

---

# Decision 015
## Реальные пользовательские данные не хранятся в репозитории

Дата:
2026-07-27

Статус:
Принято

Решение:

В GitHub запрещено хранить реальные медицинские, биометрические, контактные и иные конфиденциальные данные пользователей.

Каталог `profiles/examples/` содержит только явно обозначенные синтетические примеры. Реальные данные должны храниться в защищённой базе приложения с контролем доступа.

Причина:

Репозиторий предназначен для продукта, архитектуры, кода и обезличенных тестовых материалов, а не для персональных медицинских записей.

# Decision 016
## Модульный монолит остаётся простым

Дата:
2026-07-27

Статус:
Принято

Решение:

MVP реализуется как модульный монолит. Границы модулей определяются предметными обязанностями, но для каждого модуля не требуется обязательное разделение на четыре слоя или одинаковый набор каталогов.

Допускается объединять простые application, infrastructure и UI-компоненты, если это сохраняет ясность, тестируемость и направление зависимостей.

Причина:

Формальная многослойность для каждого небольшого модуля увеличит объём шаблонного кода до появления реальной сложности.
