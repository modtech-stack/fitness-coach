# 10. Обязательный многоэтапный review workflow

Начиная со всех следующих продуктовых этапов результат нельзя передавать владельцу
сразу после реализации и self-review.

Для каждой продуктовой задачи последовательно работают независимые роли:

`Implementer → Functional QA Reviewer → UX Reviewer → Code Reviewer`.

Каждую review-роль выполняет отдельный агент: он не участвовал в реализации
проверяемого изменения и не совмещает две review-роли в одной проверке. Implementer
не принимает окончательное решение о готовности собственной работы.

## 10.1. Implementer

Implementer:

- реализует изменение в пределах согласованного scope;
- добавляет или обновляет миграции;
- пишет и обновляет тесты;
- выполняет TypeScript, ESLint, unit tests, database/RLS tests и production build;
- проводит self-review;
- передаёт reviewers сведения о сценариях, среде и известных ограничениях.

## 10.2. Functional QA Reviewer

После Implementer отдельный Functional QA Reviewer проверяет acceptance-сценарии,
а не только код и автоматические тесты.

Для каждой новой или изменённой пользовательской функции он должен:

1. открыть работающее приложение;
2. пройти сценарий как реальный пользователь;
3. выполнить действие через UI;
4. проверить результат после перезагрузки страницы;
5. когда релевантно, проверить фактическое состояние Supabase;
6. проверить ошибки и негативный сценарий;
7. проверить пользовательские экраны на desktop и mobile.

Для CRUD проверяется полный цикл:

`create → read → update → reload → delete → persistence check`.

Для функций, зависящих от облачной инфраструктуры, локальных unit-тестов
недостаточно. Перед handoff функцию по возможности нужно проверить в
production-like среде: Vercel Preview с hosted development Supabase.

Разрушительные сценарии нельзя проверять на production-данных. Для них создаются
отдельные тестовые аккаунты и данные в безопасной среде.

Если ключевой acceptance-сценарий не удалось реально выполнить, проверка считается
незавершённой. Это явно фиксируется как blocker в `Not tested`, а итоговый verdict
должен быть `NOT READY`.

## 10.3. UX Reviewer

После успешного Functional QA отдельный UX Reviewer оценивает работающий интерфейс
глазами нового пользователя и не исходит из устройства кода или базы.

Он проверяет:

- понятность следующего действия;
- визуальную иерархию и информационную архитектуру;
- навигацию и количество действий;
- необходимость каждого поля;
- соответствие пользовательскому языку;
- оправданность free-text и закрытых классификаторов;
- discoverability функций;
- формы, validation/error/success и empty states;
- desktop, mobile и длинный контент;
- доступность редактирования;
- когнитивную нагрузку.

Каждое замечание получает severity:

- `BLOCKER` — сценарий нельзя нормально завершить;
- `MAJOR` — сценарий работает, но UX существенно мешает пользователю;
- `MINOR` — улучшение, не блокирующее использование.

Все `BLOCKER` и `MAJOR` исправляются Implementer и повторно проверяются Functional
QA до handoff. Открытый `MAJOR` допускается только после явного согласования с
владельцем. UX Reviewer не расширяет scope продукта без обоснования.

## 10.4. Code Reviewer

После функционального и UX review отдельный Code Reviewer проверяет:

- соответствие задаче и отсутствие несогласованного scope;
- регрессии;
- безопасность и RLS;
- server/client boundaries;
- migration safety;
- обработку ошибок;
- отсутствие секретов;
- тестовое покрытие;
- ненужное усложнение.

Если доступен GitHub Codex Review, для Pull Request дополнительно запрашивается его
независимый review.

# 11. Quality Gate

Задача может быть передана владельцу только когда одновременно выполнены условия:

- TypeScript — `PASS`;
- ESLint — `PASS`;
- unit tests — `PASS`;
- database/RLS tests — `PASS`;
- production build — `PASS`;
- миграции проверены;
- основные acceptance-сценарии реально пройдены;
- persistence проверен;
- UX review выполнен;
- `BLOCKER = 0`;
- `MAJOR = 0` либо открытые `MAJOR` явно согласованы владельцем;
- code review не содержит открытых критических замечаний.

Self-review Implementer не заменяет Functional QA или UX Review. Автоматические
тесты не заменяют фактическую проверку ключевой пользовательской функции через UI.

---

# 12. Цикл исправлений

Если QA или reviewer находит проблему:

`review → Implementer fixes → relevant tests repeat → Functional QA repeat → reviewer repeat when necessary`.

Повторяются только релевантные проверки, но после исправления всегда повторяется
затронутый acceptance-сценарий. Если после трёх циклов остаётся blocker, работа
останавливается: владельцу передаются причина, собранные доказательства и варианты
следующего шага вместо бесконечного цикла изменений.

---

# 13. Формат handoff report

Вместо сообщения «готово» итоговый отчёт содержит:

## Implementation

Что реализовано.

## Automated checks

Какие проверки выполнены и их фактический результат.

## Functional QA

Какие реальные пользовательские сценарии выполнены через UI и как проверен
persistence.

## Environment

Где выполнялась проверка:

- local;
- hosted development Supabase;
- Vercel Preview.

## UX Review

- `BLOCKER`;
- `MAJOR`;
- `MINOR`.

## Code Review

Вывод независимого review и состояние критических замечаний.

## Not tested

Что не удалось проверить и почему.

## Known issues

Известные проблемы и согласованные исключения.

## Verdict

Только один из вариантов:

- `READY FOR OWNER REVIEW`;
- `NOT READY`.

Запрещено писать `READY FOR OWNER REVIEW`, если ключевая функция не была реально
проверена через UI.
